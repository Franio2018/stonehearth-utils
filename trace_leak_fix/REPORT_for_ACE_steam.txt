[h1]UI memory leak in RadiantTrace: grandchild traces are never destroyed (cause of "lags more and more, then crashes after ~1h")[/h1]

[h2]Summary[/h2]
RadiantTrace._expand_uri (radiant/js/radiant/trace.js, vanilla, not overridden by ACE) destroys only the [b]direct[/b] child traces when a traced object updates. Deeper traces are orphaned: they stay registered in their Tracer, keep receiving progress and keep re-expanding. Views that live all session (unit frame, town, bulletins...) pile up duplicate traces of the same entities without limit.

[h2]Evidence[/h2]
Measured through the UI DevTools port (127.0.0.1:1338) on a 25-citizen ACE town, game AFK at 1x, nothing clicked:
[list]
[*]radiant._tracerMap['object://game/<citizen>']._traces.length went from 101 to 175 in about 10 minutes and kept climbing.
[*]Sampling heap profile (live allocations after a forced GC, 5 min window): 108 MB, mostly $.Deferred / $.Callbacks created from _expand_uri and _expand_object_properties in trace.js.
[*]The CEF renderer grew about 35 MB/min (540 MB to 2.1 GB) and died after 43 min with 0xe0000008 in KERNELBASE.dll (Chromium out of memory). The simulation kept running without a UI.
[/list]
With the fix below, the same save ran [b]4 hours[/b]: at most 5 traces per entity, total trace count flat (1200 to 1092), UI process at 600-750 MB for the first 3 hours, game still responsive.

[h2]Cause[/h2]
[code]
var trace = radiant.trace(uri)
   .progress(function (json) {
      if (json) {
         var tracesToDelete = previousTraces;
         [childDeferred, previousTraces] = self._expand_object(json, properties, ...);
         ...
         radiant.each(tracesToDelete, function (_, t) {
            delete self._traces[t.get_id()];
            t.destroy();   // removes only this trace; the traces that ITS
                           // progress callback created stay installed
         });
      }
   })
[/code]
previousTraces holds only the traces created directly by this expansion. The traces each of them created in turn live in their own closures, and nothing ever destroys them. RadiantTrace.destroy() does clean up everything through this._traces, so short-lived views are fine, but views that live all session never call it.

A second, smaller problem: a trace removed during Tracer._protectTraceList is only queued in _dead_traces, so it still gets the current update and re-expands, installing child traces nobody owns.

[h2]Fix[/h2]
UI-only, about 80 lines, works on vanilla and ACE. It patches RadiantTrace.prototype:
[code]
proto._destroyTraceTree = function (t) {
   var self = this;
   t._tlf_dead = true;
   delete self._traces[t.get_id()];
   t.destroy();
   var children = t._tlf_children;
   t._tlf_children = null;
   radiant.each(children, function (_, c) { self._destroyTraceTree(c); });
};

// in _expand_uri's progress callback:
if (trace._tlf_dead || self._destroyed) {
   return;
}
...
[childDeferred, previousTraces] = self._expand_object(json, properties, ...);
trace._tlf_children = previousTraces;
...
radiant.each(tracesToDelete, function (_, t) { self._destroyTraceTree(t); });
[/code]
_destroyAllTraces also marks every trace dead before destroying it. Merging this into trace.js directly would be the cleanest option. I'm happy to share the full file.

[h2]Not fixed yet[/h2]
After about 3 hours the UI's JS heap grows again (391 to 670 MB) while trace, view and DOM counts stay flat, so there is a second, unrelated source. The main process's native memory also grows steadily (about 22 MB/min).
